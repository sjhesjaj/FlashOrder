# M4 同步与异步对比

## 实验条件

在同一台 Windows 主机上的 Docker Desktop 29.6.2 运行 MySQL 8.4.13、Kafka 4.2.2 和 Redis 7.4.12。主机使用 i7-13650HX，Docker 可用 20 个逻辑 CPU 和约 7.6 GiB 内存。应用使用 JDK 21，同步和异步各跑一轮持续写入及售罄洪峰。每轮使用独立 MySQL schema、活动及幂等键，避免上轮的库存、Outbox 和幂等状态串入本轮。

| 条件 | 持续写入 | 售罄洪峰 |
|---|---:|---:|
| 提供请求数 | 1,200 | 500 |
| 提供速率 | 100 请求/秒 | 一次提交全部任务 |
| 初始库存 | 1,300 | 30 |
| HTTP 提交线程上限 | 64 | 64 |

两种模式都开启保护，活动令牌桶每秒补充 400 枚、容量 60。Hikari 每角色最多 10 条连接，异步在途门槛为 2,000。每轮使用一个活动和库存行，异步使用一个消费者线程，并记录实际的 Kafka 分区。同步运行 API 和取消调度器，异步另起消费者进程并在调度器启用 Relay。MySQL 实测 `innodb_flush_log_at_trx_commit=1`，`sync_binlog=1`。

## 统计口径

- 入口耗时来自逐笔 HTTP POST。负载线程复用 HTTP 连接，并分开记录计划时刻到实际发送的排队时间。先导试跑采用逐笔新建客户端，持续写入时发送前 P95 排队超过 30 秒。正式结果使用连接复用后重跑的四组数据。
- 客户端终态耗时每 10 笔抽一笔，异步以 200 ms 间隔轮询，同步建单直接使用 POST 终态。异步客户端值包含轮询和取样排队时间。
- 订单处理速率用已建单数除以首末 `finished_at` 的跨度。该字段记录事务内写状态的时间，库存更新和提交仍可能在之后。InnoDB 行锁等待使用同一个隔离 MySQL 服务的全局计数差值。
- 持续写入和洪峰都统计入口状态、持久化请求、终态、订单与 Outbox。异步排空同时核对 Kafka offset、库存差额和未发布记录。分别记录最后一次数据库受理到最后一次终态写入、最后一次 Outbox 发布的时间。

## 持续写入

| 指标 | 同步 | 异步 |
|---|---:|---:|
| 入口响应 | 1,200 × 201 | 1,200 × 202 |
| POST P95 / P99 | 624 / 971 ms | 264 / 771 ms |
| 客户端观察终态 P95 / P99 | 596 / 1,041 ms | 9,538 / 9,660 ms |
| 订单状态写入速率 | 105.8 单/s | 59.3 单/s |
| InnoDB 行锁等待次数 / 合计时间 | 502 / 21,648 ms | 0 / 0 ms |
| 最后一笔受理后的终态排空 | 0.003 s | 9.59 s |
| 最终订单数 / 库存差额 | 1,200 / 0 | 1,200 / 0 |

两种模式均在约 12.01 秒里响应全部 POST。异步入口 P95 更低，单活动的一条消费线程仍要串行完成建单事务，因此终态积压拉长了客户端等待。同步的并发扣减产生了库存行锁等待。异步命令在分区 1，最终 lag 为 0。最后一次受理后约 9.94 秒发布完命令和订单事件。

## 售罄洪峰

| 指标 | 同步 | 异步 |
|---|---:|---:|
| HTTP POST 返回 | 30 × 201，470 × 409 | 500 × 202 |
| 成功 POST 响应速率 | 14.5 份 201/s | 183.4 份 202/s |
| 入口快速售罄拒绝 | 373 笔（74.6%） | 0 笔 |
| 入口限流或在途拒绝 | 0 笔 | 0 笔 |
| 持久化售罄拒绝 | 97 笔 | 470 笔 |
| 最终订单数 / 库存差额 | 30 / 0 | 30 / 0 |
| 最后一笔受理后的终态排空 | 0.10 s | 8.95 s |
| InnoDB 行锁等待次数 / 合计时间 | 101 / 6,562 ms | 0 / 0 ms |

同步在库存归零后快速拒绝了 373 笔。异步在快照能看到售罄前已持久化全部 500 笔，消费者最终判定 470 笔售罄。这里的 202 速率衡量持久受理，成功建单共 30 笔。异步命令在分区 4，最后一次受理后约 0.50 秒发完 Outbox，终态到 8.95 秒才全部写完。最终 lag 为 0。

四轮正式实验的 Redis 失败计数均为 0。上表为本机单活动负载的观测值。不同分区的多活动并行由 N7 复查单独测量。 [N7 复查](../reviews/2026-11-19-m3-acceptance.md#n7-的代码)

原始数据包括四轮逐笔 HTTP CSV、MySQL 逐笔受理与终态 UTC 时间、按秒状态写入统计、Outbox 和 Kafka 分区摘要、行锁计数差值以及各角色 Prometheus 快照。运行标识为 `m4-experiment-261120041505728315`。

## 故障与监控验收

| 场景 | 实测结果 |
|---|---|
| 售罄、幂等与恢复 | 快速拒绝返回 `409 SOLD_OUT`，原键重放返回 `201`。取消归还库存后换用户建单成功。 |
| 用户与活动限流 | 同用户的追加请求观测到 2 次 `429 USER_RATE_LIMITED`，40 笔热点活动并发请求观测到 30 次 `429 CAMPAIGN_RATE_LIMITED`。 |
| Redis 停机 | 进程内桶在配置实例数为 2 时，两次重放或受理后拒绝超额请求，状态序列为 `202 / 202 / 429 / 429`。Actuator 健康检查仍通过，Redis 重启后观察到 Redis 桶再次生效。 |
| Kafka 停机 | 70 笔中受理 27 笔，其余 43 笔返回 `503 IN_FLIGHT_FULL`。门槛 12，实际超放 15。按本次活动桶容量 8、补充 50/s 和 1 秒标称刷新间隔，名义窗口额度是 58。 |
| Kafka 恢复 | 从发出重启命令到 27 笔全部建单约 5.75 秒，相关命令及订单事件全部发布约 5.92 秒，对账差额为 0。 |
| 监控 | Prometheus 四个 target 均为 `up`，三个应用角色以及 MySQL exporter 均可抓取。采到了 Kafka lag、终态延迟直方图、InnoDB 行锁等待与取消失败计数。 |

验收用例另外构造了一次无法归还库存的临时数据状态，确认订单事务回滚且取消失败计数上升。恢复正确库存后，下一轮取消通过。JDK 21 下 `clean verify` 的 55 项用例全部通过。M2 竞态测试先顺序准备订单，再启动原有的并发支付或取消操作，避免前置造单竞争干扰结果。
