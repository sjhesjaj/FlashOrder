# FlashOrder 产品需求文档（V1）

> 状态：V1 的 M1–M4 四个里程碑均已验收，最新提交是 `main` 上的 `aef5618`（2026-11-20）。实现细节见 [技术文档](technical-overview.md)，设计取舍见 [design-v1.md](design-v1.md) 和 [decisions.md](decisions.md)。

## 1. 背景

限量抢购要同时面对四个问题：

- **热点库存行。** 瞬时请求远多于库存，所有扣减都落在同一行上，数据库锁等待会拉长响应。
- **重复提交。** 用户网络不稳会重试。回包丢失后再提交，系统既不能多扣库存，也不能给出与实际不符的结果，比如原请求已经建单，重试却收到"售罄"。
- **占库存不付款。** 下单后不付款的库存，要在期限到后自动归还。
- **中间件故障。** Kafka 或 Redis 故障时，系统要降级运行，不能丢掉已受理的请求，也不能超卖。

FlashOrder 是限量抢购后端的 V1 原型。它在单机 Docker 环境里跑通"提交 → 建单 → 支付或超时释放 → 查到结果"的完整链路，并用同机对比实验说明异步削峰的收益和代价。

## 2. 目标与非目标

**目标**

1. **不超卖，不重复建单。** 无论并发还是故障重放，库存、订单、请求三者始终一致，对账差额为 0。
2. **请求可追踪。** 每个被受理的请求都有 `requestUid`，客户端一定能查到最终结果。
3. **重复提交结果一致。** 同一个幂等键提交多少次，都得到同一个结果。
4. **入口保护。** 提供限流、售罄快速拒绝和在途上限，中间件故障时降级运行。
5. **同机对比。** 同步和异步两种受理模式在同一台机器上对比，产出可复核的原始数据。

**非目标（V1 不做）**

真实支付和退款、多 SKU 订单、真实认证、库存分桶、读写分离、CDC（Debezium）、Kafka 事务、消费者微批扣减。

笔记本上测出的数据只用于同机对比，不能当成容量结论。

## 3. 角色

| 角色 | 诉求 | V1 中的形态 |
|---|---|---|
| 抢购用户（客户端） | 提交抢购、查询结果、支付 | HTTP 接口。用请求头 `X-User-Id` 模拟登录 |
| 运营 | 配置活动和库存，核对库存 | 没有活动管理接口，活动和库存写进数据库，`dev` 环境由启动任务预置。库存核对用对账接口 |
| 运维 | 看系统状态，处理故障 | 健康检查、Prometheus 指标。API、Relay 和消费者可以拆成独立进程 |

## 4. 业务规则

| # | 规则 |
|---|---|
| B1 | 一个活动对应一个 SKU，库存独立分配，每单一件。 |
| B2 | 活动有起止时间，按受理时的数据库时间判断是否在窗口内。窗口内受理的请求，活动结束后才处理也有效。 |
| B3 | 一个用户在一个活动里最多持有一个待支付或已支付的订单。 |
| B4 | 支付期限 15 分钟，从建单时起算。到期未付的订单自动取消，归还库存，释放购买资格。活动仍开放时，用户可以换一个新的幂等键再抢。 |
| B5 | 每次提交必须带幂等键，长度 1–128，只能用可见 ASCII 字符。同键重复提交返回同一结果，并标记为重放。同一个键换了活动，返回 `409 IDEMPOTENCY_CONFLICT`。 |
| B6 | 同一活动内近似先到先得，不保证严格按提交顺序。 |
| B7 | 支付是模拟的。同一支付键重放原结果，已取消或已过期的订单拒绝支付。 |
| B8 | 系统失败（`SYSTEM_FAILED`）的请求，用原幂等键重放返回 `409 REQUEST_FAILED`，客户端换键重试。 |

## 5. 功能需求

| ID | 需求 | 验收标准 | 里程碑 | 状态 |
|---|---|---|---|---|
| FR-1 | 提交抢购请求 | 同步模式直接返回终态：`201` 建单成功，`409` 售罄或已持有。异步模式受理后返回 `202`，带 `requestUid`、`Location` 和 `Retry-After`。200 个用户争 50 件库存，恰好生成 50 笔订单 | M1、M3 | 已验收 |
| FR-2 | 查询请求结果 | 只能查自己的请求，查别人的返回 `404`。处理中时返回 `ACCEPTED`，带 `Retry-After`。结果分四种：`ACCEPTED`、`ORDER_CREATED`、`REJECTED`、`SYSTEM_FAILED` | M1、M3 | 已验收 |
| FR-3 | 查询订单 | 返回订单状态，以及 UTC 格式的支付截止时间 | M1 | 已验收 |
| FR-4 | 幂等提交 | 同一个键 40 份并发：数据库里只有 1 条请求，最多 1 笔订单。40 个响应的状态码和结果都相同，其中 39 个带 `Idempotent-Replayed: true`。零库存时只有一条 `REJECTED(SOLD_OUT)` 请求，没有订单，也没有订单事件 | M1 | 已验收 |
| FR-5 | 模拟支付 | 截止前支付成功，返回 `200 PAID`。重复支付重放原结果。支付时已过期或已取消，返回 `409` | M2 | 已验收 |
| FR-6 | 超时取消 | 到期订单取消并归还库存。两个取消任务同时运行、支付等锁一直等到过期，都只产生合法的状态转换。用户换键后能再次建单 | M2 | 已验收 |
| FR-7 | 库存对账 | `GET /admin/campaigns/{id}/reconciliation` 返回库存差额、请求与订单的对应差异，以及 `consistent` 字段 | M2 | 已验收 |
| FR-8 | 异步受理与失败恢复 | 受理后立刻能查到请求。下面三类故障注入后，原请求都可查，同一请求最多一单：提交后 HTTP 回包丢失、Relay 收到 Kafka ACK 后标记前崩溃、消费者提交数据库后提交 offset 前崩溃。毒消息最终变成 `SYSTEM_FAILED`，并进入死信主题 | M3 | 已验收 |
| FR-9 | 入口保护 | 四种快速拒绝：用户级限流和活动级限流返回 `429`，售罄返回 `409 SOLD_OUT`，在途已满返回 `503 IN_FLIGHT_FULL`，都带 `Retry-After`。用户级限流之后先按原幂等键回查，所以已有请求的重放优先于售罄、活动限流和在途拒绝。快速拒绝不写请求记录 | M4 | 已验收 |
| FR-10 | 故障降级 | Kafka 停机时，在途上限以内继续受理，超过后返回 `503`。恢复后积压能清空，并记录清空时间。Redis 停机时，限流降级为进程内令牌桶 | M4 | 已验收 |
| FR-11 | 可观测性 | 提供三类信息：<br>• 健康检查；<br>• Prometheus 指标：受理与终态延迟、连接池、Kafka lag、InnoDB 行锁等待、入口拒绝计数、支付、取消、对账差额；<br>• 后台角色的独立管理端口 | M1–M4 | 已验收 |
| FR-12 | 对比实验 | 同步和异步各跑一轮持续写入和售罄洪峰，原始数据和报告入库 | M4 | 已验收 |

## 6. 接口概览

| 接口 | 用途 |
|---|---|
| `POST /campaigns/{campaignId}/purchase-requests` | 提交抢购，需要请求头 `X-User-Id` 和 `Idempotency-Key` |
| `GET /purchase-requests/{requestUid}` | 查询请求结果 |
| `GET /orders/{orderUid}` | 查询订单 |
| `POST /orders/{orderUid}/payments` | 模拟支付，需要请求头 `X-User-Id` 和 `Idempotency-Key` |
| `GET /admin/campaigns/{campaignId}/reconciliation` | 库存对账 |

响应码的完整规则见 [技术文档的接口一节](technical-overview.md#9-接口与响应码)。

## 7. 非功能需求

| 类别 | 要求 | V1 的做法 |
|---|---|---|
| 一致性 | 对账恒等式 `total = available + 待支付 + 已支付` 始终成立；每个请求最多一单；每个用户每个活动最多一个活跃订单 | 由数据库约束和事务保证：CHECK 约束、生成列上的唯一索引、保存点，以及固定的加锁顺序 |
| 持久性 | 只要返回了 `202`，请求就不会丢 | 受理事务提交后才返回响应。请求和建单命令写在同一个事务里（Outbox） |
| 可用性 | Kafka 或 Redis 故障时继续提供有界的服务 | Kafka 停机时按在途上限继续受理，Redis 停机时改用进程内令牌桶 |
| 性能 | V1 没有 SLA 指标，只要求同机对比可复核 | 见下方实测参考，原始数据见 [M4 对比实验](experiments/m4-comparison.md) |
| 可运维 | 角色能拆开部署，后台角色也能被监控 | 三种 Spring profile：`api`、`scheduler`、`consumer`。加上 `ops` profile 后，后台角色开放管理端口 18081 和 18082 |
| 可测试 | 并发和故障场景都有自动化测试 | 59 项测试，其中 39 项是 Testcontainers 集成测试，使用真实的 MySQL、Kafka 和 Redis |
| 环境 | Windows 上直接可跑 | JDK 21 + Docker Desktop + Maven Wrapper，不依赖 bash 和 make |

**实测参考（本机单活动，开启保护）：**

| 场景 | 同步 | 异步 |
|---|---:|---:|
| 持续写入 100 请求/s：POST P95 | 624 ms | 264 ms |
| 持续写入 100 请求/s：客户端看到终态的 P95 | 596 ms | 9,538 ms |
| 持续写入：订单写入速率 | 105.8 单/s，未饱和 | 受理期间 48.9 单/s，之后 70.8 单/s |
| 持续写入：InnoDB 行锁等待次数 | 502 | 0 |
| 售罄洪峰 500 笔抢 30 件：最终订单 / 库存差额 | 30 / 0 | 30 / 0 |

结论：异步入口延迟更低，没有行锁等待，代价是结果要晚出来。单活动的库存吞吐受一条消费线程串行建单的限制，不比同步高，这与设计预期一致。

## 9. 风险与待定事项

| 项 | 说明 | 处理 |
|---|---|---|
| 单活动吞吐上限 | 一个活动的命令进同一个分区，由一条线程逐单建单。本机约 50–70 单/s | V1 接受这个限制。提升方向是消费者微批，见第 10 节 |
| 同步模式的容量上限 | 提到每秒 200 个请求时，同步达到 137.8 单/s，但客户端已经开始排队，上限还没测出来 | 需要时另做饱和测试 |
| 认证是模拟的 | 用 `X-User-Id` 冒充登录，不能上公网 | V1 不做 |
| Redis 恢复较慢 | Redis 长时间停机后恢复，要等 Lettuce 重连成功才切回，最长约 30 s。这期间按本地配额限流，限流不会放松 | 已写入设计稿 |
| 遗留观察项 | N2：每次支付成功后要多查一次。N14：活动数量变多后，快照查询会变慢。N15：`dev` 一体进程的调度线程不够用 | 不影响 V1 的结论，按验收记录里给的时间处理 |

## 10. 后续方向（待定）

3. **库存分桶、读写分离。**
4. **用 CDC 替代轮询式 Relay。**
