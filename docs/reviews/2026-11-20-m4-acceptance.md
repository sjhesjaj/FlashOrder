## 逐项核对

- **入口顺序**（[PurchaseProtection.java](../../src/main/java/com/flashorder/request/PurchaseProtection.java)）：顺序是用户限流 → 幂等回查 → 活动窗口和售罄快照 → 活动限流 → 异步在途门槛 → 受理事务，与设计稿 1.2 节和 R3 一致。
  - 任何一道快速拒绝命中后，都会再查一次幂等键。这样并发的原请求如果已经提交，重试拿到的是原结果，不是拒绝。
  - 幂等回查之后才扣活动配额，重放不消耗活动配额。
- **Redis 令牌桶**（`token-bucket.lua`）：
  - 用 Redis 的 `TIME` 计时，单键原子更新。
  - 时钟回拨时，桶的时间不往回走。
  - 过期时间等于桶补满所需的时间，再加上时钟回拨的差值，所以键过期之前桶一定已经补满。
- **本地降级**（[PurchaseRateLimiter.java](../../src/main/java/com/flashorder/request/guard/PurchaseRateLimiter.java)）：
  - 调用 Redis 失败或返回值异常时，暂停使用 Redis 1 s。暂停期间所有请求走本地桶，到时间后只放一个请求去探测。
  - 本地桶的速率和容量都按实例数分摊。配置校验保证分摊后的容量不低于 1 枚。
  - 本地桶最多保存 10,000 个键，满了以后对新键直接拒绝。这是为了限制内存而故意选择失败时拒绝。代价是：Redis 停机期间，单个实例如果 2 s 内遇到超过 1 万个新用户，多出的新用户会收到 `USER_RATE_LIMITED`。第一版可以接受。
- **售罄与窗口快照**（[CampaignProtectionSnapshot.java](../../src/main/java/com/flashorder/request/guard/CampaignProtectionSnapshot.java)）：
  - 用读取时拿到的数据库时间，加上单调时钟推算当前时间，再在窗口两端各留一个刷新周期。边界附近交给受理事务判断。
  - 只有活动确定处在窗口内、且 `available = 0` 时才快速拒绝售罄。活动不在窗口内时，`LEFT JOIN` 得到的 `available` 是 NULL，不会被当成售罄。
- **在途门槛**：
  - 每秒批量统计一次各活动的 `ACCEPTED` 数，样本最长使用 3 s。
  - 采样失败或样本过期时，改为每个请求查一次单个活动，走 V3 新增的 `(status, campaign_id)` 索引。
  - gauge 显示的是最近一次成功的样本。
- **消费者**：
  - 终态延迟的算法是：锁定读时 MySQL 返回的已受理时长，加上从查询发出到提交完成的单调时钟耗时。只在提交成功后记录。
  - `recover` 改成先解析命令再加锁。我对照了重构前的代码，两者行为相同，因为 `lockMatchingRequest` 不会抛 `Invalid`。
- **Relay 日志**（N9）：只在状态切换时打日志，进入降级打 WARN，恢复打 INFO，降级期间的其余日志改为 DEBUG。另外新增四个计数器：已领取、已发布、已安排重试、结果未定。我的 Kafka 停机演练里，24 s 内只有一条 WARN 和一条 INFO。
- **监控**（F7、N3）：
  - `ops` profile 给 scheduler 和 consumer 单独开管理端口（18081、18082），只监听 127.0.0.1。
  - compose 新增 mysqld-exporter 和 Prometheus。Hikari 连接池上限显式配置为 `FLASHORDER_DB_POOL_SIZE`，默认 10。
  - Redis 的健康检查关掉了，所以 Redis 停机时 API 的健康状态不会变成 DOWN。
- **取消任务**（N1）：新增失败计数 `flashorder.order.expiry.failures`，异常照常抛出。
- **测试夹具**（`fc61671`）：M2 的竞态测试改成先逐个造好订单，再并发跑支付或取消。被测的竞争仍然是并发的，只是造数据这一步不再抢同一行库存。
- **文档**：G8 已写入设计稿 1.2 节，`decisions.md` 里标为采纳；原来"缓存最多滞后 200 ms"那句也改掉了。README 新增了 M4 一节，说明配置、端口和压测器的用法。

## 核对实现方的数据

证据包里有逐笔的 HTTP CSV、MySQL 的受理和终态时间、各角色的 Prometheus 快照。下面这些结论是我从原始数据里重新算出来的：

- **异步终态延迟**：用服务端的 `finished_at − accepted_at` 算，P95 是 9.42 s，客户端观察到的是 9.54 s。差值约 0.1 s，就是 200 ms 轮询带来的。轮询线程池只有 16 个线程，但没有明显推高结果。
- **同步入口延迟**：请求行从受理到写终态的 P95 只有 11 ms，而 POST 的 P95 是 624 ms。按 API 进程的 Hikari 指标，连接获取总耗时 113.2 s，持有总耗时只有 41.0 s，共获取 2,495 次。**同步入口延迟的大头是排队等连接**，见 N12。
- **异步消费速率**：按秒统计，受理还在进行时，消费速率约 45–55 单/s；POST 结束后升到 65–80 单/s。报告里的 59.3 是两段的平均。
- **售罄洪峰**：同步模式下持久化了 127 行，其中 30 笔建单、97 笔售罄；另外 373 笔是快速拒绝，合计 500 笔。异步模式 500 笔全部持久化，其中 470 笔售罄。两种模式的库存差额都是 0。
- **Redis 停机**：实现方的冒烟脚本只测了用户级。它用同一个用户、同一个幂等键连发 4 次，所以只能说明用户桶在降级后仍然生效。活动级降级由我补测。

## 我的复测（临时 compose：MySQL 8.4、Kafka 4.2.2、Redis 7.4.12、mysqld-exporter、Prometheus；`a698f70` 打包出的 jar）

**Lua 令牌桶（直接对真实 Redis 调用脚本，速率 5/s，容量 10）**：连调 12 次，前 10 次放行、后 2 次拒绝。1 s 后再调，放行 5 次后开始拒绝。空闲 2.2 s 后键已过期。

**同步模式的入口拒绝（默认配额）**：

| 场景 | 响应 | 是否写入请求行 |
|---|---|---|
| 库存 1，第一位用户 | `201 ORDER_CREATED` | 写 |
| 快照刷新后，第二位用户 | `409 NOT_ACCEPTED / SOLD_OUT`，`Retry-After: 1` | 不写 |
| 第一位用户用原键重放 | `201`，`Idempotent-Replayed: true` | — |
| 尚未开始的活动 | `409 CAMPAIGN_CLOSED` | 不写 |
| 不存在的活动 | `404 CAMPAIGN_NOT_FOUND` | 不写 |
| 同一用户用 14 个不同的键并发提交 | 放行 10 笔（1 笔建单、9 笔 `ALREADY_HOLDING`），4 笔 `429` | — |
| 40 个用户并发抢同一活动 | 24 笔 `201`（突发 20 加上补充），16 笔 `429`，`Retry-After: 1` | — |

**Redis 停机（`instances=2`）**：

| 场景 | 结果 |
|---|---|
| `docker stop` 期间，每秒约 9 笔请求 | 全部 `201`。大约每 1.1 s 有一笔多花约 100 ms（探测请求等满命令超时），其余中位数 20 ms，和停机前一样。 |
| `docker stop` 期间，40 个用户并发 | 12 笔 `201`，28 笔 `429`，说明本地活动桶按 10 的突发容量生效。 |
| `docker pause`（连接还在但不回包） | 延迟规律相同，慢请求 115–125 ms。40 个用户并发时 13 笔 `201`、27 笔 `429`，最慢 108 ms。 |
| 约 10 s 的短时停机后恢复 | 恢复后第 2 笔请求就回到 Redis。 |
| 45 s 的长时停机后恢复 | **Redis 恢复健康 16.6 s 后**限流才回到 Redis。日志显示，Lettuce 的重连间隔已经退避到 30 s。见 N11。 |

**Kafka 停机（默认门槛 500，活动配额 200/s、突发 20）**：停掉 Kafka 后，压测器以 300/s 的速度提交 1,500 笔。

- **入口**：693 笔 `202`，562 笔 `429 CAMPAIGN_RATE_LIMITED`，245 笔 `503 IN_FLIGHT_FULL`，POST 的 P95 是 214 ms。
- **在途数量**：`ACCEPTED` 以每秒约 215 笔的速度上涨，停在 693，超放 193，没有超过上界。
- **恢复**：Kafka 停机 24 s 后重启。从重启算起，4.05 s 发完全部命令，7.32 s 健康检查通过，15.54 s 后 693 笔全部建单。消费者速率 59.9 单/s，对账差额 0。

**监控**：Prometheus 的四个采集目标全部在线。在途数量的 gauge 峰值是 693，Outbox 未发布行数的峰值也是 693。终态延迟直方图、Kafka lag 和 InnoDB 行锁等待都有数据。

**重跑对比实验（配置同报告：活动配额 400/s、突发 60，异步门槛 2,000，单消费线程）**：

| | 同步 100/s | 异步 100/s | 同步 200/s（饱和测试） |
|---|---:|---:|---:|
| 入口响应 | 1,200 × 201 | 1,200 × 202 | 1,200 × 201 |
| POST P95 / P99 | 327 / 510 ms | 43 / 388 ms | 514 / 661 ms |
| 客户端观察终态 P95 | — | 7.24 s | — |
| 订单写入速率 | 103.8 单/s | 64.0 单/s | **137.8 单/s** |
| InnoDB 行锁等待 | 358 次 / 11.6 s | 0 | 1,198 次 / 69.5 s |
| 客户端发送前排队 P95 | 0.7 ms | 0.7 ms | 2.17 s |

同步售罄洪峰（500 笔抢 30 件）：30 笔 `201`，470 笔 `409 SOLD_OUT`，其中快速拒绝 425 笔（85%），持久化售罄 45 笔，库存差额 0。

两种模式的结论方向和报告相同：异步入口更快，终态积压更久；异步消费线程是单活动的上限。具体数字受主机负载影响。同步 200/s 这一列说明，**同步在 100/s 下并没有饱和**，见 N12。

测试环境已用 `down -v` 拆除。

## 不阻塞的观察

| # | 观察 | 建议时间 |
|---|---|---|
| N11 | **Redis 长时间停机后，限流器要等 Lettuce 重连才能回到 Redis。**<br>• **现象**：Lettuce 的重连间隔按指数退避，最长 30 s。实测停机 45 s，Redis 恢复 16.6 s 后限流才回到 Redis。<br>• **原因**：应用每秒发一次的探测改变不了这一点。连接断开期间，命令只是排在 Lettuce 的缓冲里，等满 100 ms 超时后失败。<br>• **影响**：限流不会放松，只是继续按本地分摊的配额执行，恢复变慢。设计稿 1.2 节"约 1 秒探测恢复"的说法，在长时间停机后不成立。<br>• **建议**：用 Spring Boot 的 `ClientResourcesBuilderCustomizer`，把 Lettuce 的重连退避上限压到约 1 s。还可以把 `disconnectedBehavior` 设为 `REJECT_COMMANDS`，断开期间探测立即失败，不用再等 100 ms。如果不改代码，就在设计稿里写明，恢复时间受重连退避约束，最长约 30 s。 | V1 收尾前 |
| N12 | **实验报告有三处口径要补充。**<br>• **同步写入速率**：表里的 105.8 单/s 就是提供速率（100/s），同步并没有饱和。我把提供速率提到 200/s，同步达到 137.8 单/s，这时客户端已经开始排队，所以这还不一定是上限。本机上单活动同步的写入速率至少是异步消费线程的 2 倍左右，差距比表面数字更大。建议在表下注明这一点，或者补一轮饱和测试。这和设计稿"库存 TPS 不会更高"的预期一致。<br>• **同步入口延迟的构成**：入口 P95 主要是排队等连接，不是事务内部的耗时。实现方数据里，连接获取总耗时 113.2 s，持有只有 41.0 s，请求行从受理到终态的 P95 只有 11 ms。10 条连接把排在热点行后面的事务挡在了连接池外面。另外，保护开启后每笔新请求要取两次连接，一次幂等回查，一次受理事务。"热点还卡在哪里"这个问题，这组数据正好能回答。<br>• **异步消费速率分两段**：受理期间约 50 单/s，受理结束后约 70 单/s，两段共用同一个 MySQL 的刷盘。59.3 是平均值，建议分开写。<br>另外，证据包放在仓库外，报告只写了运行标识。建议把证据包（342 KB）放进仓库，或者写明存放位置。 | 实验数据对外使用前 |
| N13 | **保护链路没有自动化集成测试。**<br>• **现状**：新增的 16 项测试都基于 mock。Lua 脚本、控制器对 `429`/`503`/`409` 和 `Retry-After` 的映射、Redis 停机降级、Kafka 停机时的在途门槛，都只靠实现方仓库外的冒烟脚本和我的手工复测来验证。<br>• **建议**：用 Testcontainers 起一个 Redis（`redis:7.4`），补一个集成测试，至少覆盖三项：令牌桶放行和拒绝、每种拒绝码的 HTTP 响应、Redis 停掉后走本地桶。或者把冒烟脚本放进 `scripts/`。 | V1 收尾前 |
| N14 | **快照查询会随数据增长变慢。**<br>• `readCampaigns` 每 200 ms 读一遍全部活动，没有按时间过滤。<br>• 在途采样失败后，回退路径对每个请求执行一次 `COUNT(*)`，数到门槛也不停。<br>• **建议**：快照只读窗口附近的活动。其余活动交给数据库判断，结果不变。回退统计用子查询加 `LIMIT` 截断到门槛。 | 活动数量变多时 |
| N15 | **`dev` 一体进程的调度线程不够用，快照可能过期。**<br>• 这个进程只有 2 个调度线程，要同时跑 Relay（每轮最长 1 s）、取消任务、Outbox 计数和两个快照刷新。<br>• 售罄快照可能因此超过 600 ms 没刷新，快速拒绝会悄悄停掉。<br>• **影响**：结果仍然正确，只是失去快速拒绝。只影响一体进程，实验用的是分进程部署。这一条是根据代码推断的，没有实测。<br>• **建议**：给快照刷新单独开一个调度器，或者在 `dev` 下调大调度线程池。 | 不急 |

### N13：集成测试

[PurchaseProtectionIntegrationTest.java](../../src/test/java/com/flashorder/PurchaseProtectionIntegrationTest.java) 用 Testcontainers 起 Redis 7.4.12 和 MySQL，以 `api` 角色、异步受理、随机端口启动，测试通过真实 HTTP 发请求。共 4 项测试：

1. **Lua 双层突发**：用户桶和活动桶各放行 4 笔，第 5 笔返回 `429`。测试把 Redis 里的 `updated_at` 往后推 60 秒，借 Lua 的时钟回退保护冻结补充，这样主机停顿不会让断言抖动。这一步顺带覆盖了时钟回退分支。
2. **售罄**：等快照标出售罄后再请求，返回 `409 SOLD_OUT`，请求表里没有新行。
3. **在途门槛**：测试不运行 Relay，4 笔请求一直停在 `ACCEPTED`。删掉活动桶后，新请求返回 `503 IN_FLIGHT_FULL`。用原键重放仍然得到原来的 `202`，body 不变，带 `Idempotent-Replayed: true`。
4. **Redis 停机**：按 4 个实例分摊后，用户和活动的本地突发容量都是 1。同一用户的第二笔请求返回 `429 USER_RATE_LIMITED`，换一个用户返回 `429 CAMPAIGN_RATE_LIMITED`。Redis 失败计数增加。

每次拒绝都检查三件事：`Retry-After: 1`，body 里没有 `requestUid`，请求表和未发布的 `CREATE_ORDER` 行数没有变。

我还检查了第 4 项会不会因时序误放行。本地桶的补充速率是每秒 0.25 个令牌，补回 1 个要 4 秒。每次探测最多等 1 秒超时，而且冷却期内只探测一次。三笔请求之间远不到 4 秒，所以不会误放行。

下面三项没有覆盖，都不影响关闭 N13：

- 保护链路上的窗口外 `409` 和不存在活动的 `404`。这两项我在验收复测里手工测过。
- Redis 恢复后切回（N11 的行为）。
- 真实的 Kafka 停机。测试用"不运行 Relay"代替，端到端结果见上文的故障演练。
