## A. 底座处理

**结论**：新建工程。从 `burst-safe-inventory`（提交 `801b695`，MIT）借两样：并发集成测试的写法，以及 `stress/stress.py`。压测脚本复制进来，文件头保留 MIT 声明。README 注明参考来源。

**理由**：

- 原仓库可复用的代码很少。`src/main` 下 14 个 Java 文件放在同一个包里，核心逻辑约 100 行，都要按 MySQL 重写。
- 单包结构撑不起三种角色。
- 原 README 自带一段 "Resume bullet"，fork 关系会让面试官先问"哪些是你写的"。
- 迁移 MySQL 有具体的坑：原幂等逻辑依赖 Postgres 的 `ON CONFLICT DO NOTHING` 加 `READ COMMITTED` 下每条语句一个新快照。MySQL 默认 `REPEATABLE READ`，事务第一次读取就固定快照，撞键等待结束后再读也看不到赢家的结果。

## A1. 包结构与角色

**结论**：分 `request`、`order`、`inventory`、`outbox`、`common` 五个包。三个 profile：`api`、`consumer`、`scheduler`。Outbox Relay 和超时取消一起放在 `scheduler`，两者都是定时轮询数据库的后台任务。另设 `flashorder.intake-mode=sync|async` 开关，供同步与异步对比。

## B. 支付不碰库存行

**结论**：库存行只维护 `total` 和 `available`，预留数和已售数从订单状态统计。不变量改为 `total = available + 待支付数 + 已支付数`。

**理由**：原稿的支付要改"预留 -1，已售 +1"，建单、支付、超时三条路径会抢同一行。改成统计之后，支付只改订单行。代价是对账要做 `COUNT`，有 `(campaign_id, status)` 索引就够。

## C. 资格合并进订单表

**结论**：`purchase_order` 加生成列 `active_flag = IF(status IN ('PENDING','PAID'), 1, NULL)`，再建 `UNIQUE(campaign_id, user_id, active_flag)`。去掉原稿的 `PURCHASE_CLAIM` 表。

**理由**：单独建资格表的话，要自己处理"释放后再占"。合并之后，"资格 = 活跃订单"由数据库约束保证，订单取消时资格自动释放，少一张表，也少一处同步。

## D. 售罄快速拒绝

**结论**：可用库存为 0 时，入口直接返回 `409 SOLD_OUT`，不写记录。

**理由**：超时会归还库存，所以售罄不是永久状态。不做快速拒绝的话，售罄洪峰会全部落到受理事务的插入上。

## 1–3, 6. 其余设计点

- **分区键用 `campaign_id`**：同一活动的命令进一个分区、由一个消费者依次处理，消费者之间不在库存行上排队。
- **全局 `READ COMMITTED`**：撞键后能读到对方结果；超时扫描时不加间隙锁。唯一键检查照样加锁。
- **加锁顺序**：先锁请求或订单行，最后更新库存行并立即提交。超时批量归还按 `campaign_id` 升序更新。
- **失败路径**：业务拒绝直接写终态。技术异常退避重试 3 次，用尽后标成 `SYSTEM_FAILED` 并转入死信主题。同一幂等键返回原结果。

## R. 写入设计时的细化

**R1. 售罄缓存改为直接读 MySQL，不用 Redis 标记。** 每个 API 实例每 200 ms 非加锁读一次 `available`。原方案要求消费者置标记、超时任务清标记，任何一次 Redis 写失败都会让标记残留，导致误拒。直接读库没有这条双写链路，库存归还后最多 200 ms 自动恢复。非加锁读不和热点行争锁。

**R2. 在途上限按 `ACCEPTED` 请求数统计，不按未发布的 outbox 行数。** 后者只反映 Relay 停摆。前者在 Relay 停摆和消费者停摆时都会上涨，更贴近"受理后多久能给结果"。

**R3. 按幂等键查已有请求，放在所有快速拒绝之前。** 否则用户回包丢失后重试，可能收到"售罄"或"限流"，而原请求其实已经建单，用户以为没抢到，订单就会超时取消。这一步是唯一索引上的点查，代价很小。用户级限流仍然排在它前面，防止有人用大量请求刷这次查询。

## E. 框架版本

**结论**：Java 21 + Spring Boot 4.1.2，固定补丁版本。

**依据**：Spring 官方支持表显示，3.5.x 的开源支持已于 2026-06-30 结束，4.1.x 的开源支持到 2027-07-31。2026-11-19 核实，当前正式补丁版本是 4.1.2（2026-10-22 发布）。 [Spring 官方支持数据](https://api.spring.io/projects/spring-boot/generations)

**代价**：网上的教程大多还是 3.x 写法。Jackson 换成了 3.x，包名有变化。部分自动配置拆成了独立的 starter。

## F. 数据访问

**结论**：MyBatis Spring Boot Starter 4.1.0，用 Mapper 接口 + XML 手写全部 SQL，事务边界放在应用服务层。

**依据**：

- Starter 4.1.0 于 2026-07-16 发布，基于 Spring Boot 4.1.0 和 mybatis-spring 4.1.0 构建。 [MyBatis 版本兼容说明](https://github.com/mybatis/spring-boot-starter#requirements) · [Starter 4.1.0 发布说明](https://github.com/mybatis/spring-boot-starter/releases/tag/mybatis-spring-boot-4.1.0)
- 建单、支付、超时回收和 Outbox 都有各自的 SQL 和结果映射。用 Mapper 管理这些语句，事务边界留在应用服务层，代码更容易顺着业务流程读。
- 不用 JPA，因为核心的条件更新和加锁读必须完全显式。

**代价**：JdbcTemplate 一样能手写 SQL，而且和底座的写法更接近，借鉴时改动更少。选 MyBatis 要多维护一层 Mapper XML。

## G. 设计评审修订（2026-11-19）

G1、G2、G6–G8 是评审中提出的，G3–G5 是核对 G1 时补充的。

### M1：已合入设计稿

**G1. 售罄等业务拒绝与请求行在同一个事务里提交。**

- 问题：原写法在 sync 模式下库存不足时，先回滚整个事务，再另开事务插入 `REJECTED(SOLD_OUT)`。回滚会释放唯一键，同键的第二笔请求可以抢先写入，第一笔随后撞键。定稿没有规定这时第一笔该返回什么。
- 结论：请求行之后、候选订单之前设一个保存点。售罄或已持有资格时只回滚到保存点，然后在原事务里把请求标成 `REJECTED` 并提交。async 消费者用同样的写法，原来的第二个事务去掉。技术异常仍然整个事务回滚。
- 新增验收：零库存下，同一个键 40 份并发，40 个响应指向同一个拒绝结果；数据库里只有一条请求，零笔订单，零条订单事件。

**G2. 订单表补 `UNIQUE(order_uid)`。** 订单查询和支付都按 `order_uid` 定位订单。这个约束随 M1 的 Flyway 建表一起加上。

**G3. 重放的响应码只由请求当前状态决定。** 原接口表规定重放返回 `200`，于是 G1 那条验收里会是 1 个 `409` 加 39 个 `200`，不好断言，客户端也难处理。改成 `ACCEPTED`→`202`、`ORDER_CREATED`→`201`、`REJECTED`→`409` 加原因、`SYSTEM_FAILED`→`409 REQUEST_FAILED`。重放的响应额外带 `Idempotent-Replayed: true` 头。

**G4. MyBatis 一级缓存作用域设为 `STATEMENT`。** 默认的 `SESSION` 作用域下，同一事务里重复执行相同的查询会直接命中缓存，不发 SQL，`SELECT ... FOR UPDATE` 也就等于没有加锁。

**G5. 外键只指向 `campaign`，或指向本事务已经锁住的行，任何表都不引用 `inventory`。** InnoDB 插入子表行时，会对父表那一行加共享锁。如果订单表引用库存行，sync 模式下两个线程会各自拿着库存行的共享锁，再同时要升级成排他锁，形成死锁。

### M3 和 M4 修订

**G6. Relay 改成租约领取。** 原写法在等 Kafka ACK 期间一直占着数据库事务和连接。短的 `delivery.timeout.ms` 也管不住 `send()` 本身的阻塞，那段阻塞由 `max.block.ms` 控制，默认 60 秒。改法如下：

1. 开一个短事务，用 `FOR UPDATE SKIP LOCKED` 选出一批记录，写入 `lease_token` 和 `lease_until`，然后提交。
2. 在事务外发送到 Kafka。
3. 收到 ACK 后，按 `WHERE id IN (...) AND lease_token = ?` 回写 `published_at`。

`max.block.ms` 和 `delivery.timeout.ms` 都要调小，租约时长要大于两者之和。outbox 表加 `lease_token`、`lease_until` 两列。

**G7. 失败标记和死信写进同一个事务。** 原写法是先提交 `SYSTEM_FAILED`，再发死信。如果在两步之间崩溃，重投的消息会因为请求已是终态而直接结束，这条死信就丢了。改为由 recoverer 开一个事务：先锁住请求行，确认它还不是终态；然后把请求标成 `SYSTEM_FAILED`，同时写一条死信 outbox 行，`event_id` 由请求 id 派生；提交后再确认原消息。死信由 Relay 发出。

**G8. 在途上限是软门槛，售罄缓存要有过期规则。**

- 各实例每秒才刷新一次 `ACCEPTED` 数量，两次刷新之间可能超放。全局限流排在在途上限前面，所以超放量的上界是"全局限流速率 × 刷新间隔"。M4 验收要记录实测的超放峰值，并对照这个上界。
- 每个售罄缓存值记下读取时间，超过 3 个刷新周期（600 ms）没有刷新成功，就停止用它做快速拒绝，请求照常往后走限流和受理事务。
- R1 里"最多 200 ms 自动恢复"这句话，只在刷新成功时成立，写入时一并更正。
